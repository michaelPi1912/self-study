## Case P41: Adding a NOT NULL column

**Interview prompt.** Hi, this is from last Thursday's release. We had a small change planned: add a new column to an existing table in our main database. The column is marked NOT NULL, because the business said it must always have a value. The code change was tiny and all the unit tests were green. The migration ran as part of the deployment pipeline. But the deployment failed during the migration step, and the new version never went live. The table is not empty: it already holds a lot of rows from production. The release was blocked for a few hours and the team was under pressure. You were the engineer on call. Please walk me through how you would handle this incident.

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How did you prove it was the cause? Where did you look, and what did you see?
2. What would you monitor or check afterwards, especially on a large production table?
3. What is the trade-off of your fix? Does it have a risk for locking, downtime or rollback?

**Key vocabulary**
- database migration / schema migration
- deployment pipeline / the deploy failed
- existing rows / production data
- constraint violation
- to roll back a migration
- zero-downtime deployment
- to reproduce an issue in staging
- post-mortem (blameless)

**Pronunciation tips:** "migration" = /maɪˈɡreɪʃən/; "constraint" = /kənˈstreɪnt/; "schema" = /ˈskiːmə/ ("sk", not "sh").

## Case M03: Dual write to DB and Kafka

**Interview prompt.** Hi, this one comes from our order platform. When a customer places an order, our service saves it in the database and also publishes an event to Kafka, so that other teams, like shipping and billing, can react. Everything looks fine in normal traffic. But last week the support team reported something strange. Once in a while, there is an order in the database with no matching event, so shipping never hears about it. And sometimes it is the opposite: there is an event on the topic, but no order in the database. It does not happen often, and we cannot make it happen on demand. There are no obvious errors in the dashboards. Finance noticed the mismatch during reconciliation. You are the senior engineer asked to look into it. How would you approach it?

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How did you prove it was the cause, given that you cannot reproduce it on demand?
2. What would you monitor afterwards to detect this kind of inconsistency early?
3. What is the trade-off of your fix? What does it cost in complexity, latency or delivery guarantees?

**Key vocabulary**
- data consistency / inconsistency
- event-driven architecture
- at-least-once vs. exactly-once delivery
- idempotent consumer
- reconciliation
- intermittent / hard-to-reproduce issue
- eventual consistency
- distributed transaction

**Pronunciation tips:** "idempotent" = /ˌaɪdemˈpoʊtənt/; "Kafka" = /ˈkɑːfkə/; "consistency" = /kənˈsɪstənsi/.
