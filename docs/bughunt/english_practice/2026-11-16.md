## Case J10: The frontend shows no error, but the request failed

**Interview prompt.** Hi, this one came in from the frontend team. A user was filling in a form in our web app and clicked "Save". Nothing happened: no error message, no red banner, just a spinner that stopped. The user clicked three more times and then called support. The frontend developer looked at the network tab and says the request to our API shows HTTP 200 every time, so the UI treats it as a success. But when she opens the response body, she sees `{"success": false}` with an error inside. Our monitoring dashboard also shows a healthy API with almost no errors, even though support says many users complain. The frontend lead is frustrated and asks you, as the backend engineer, to explain what is going on and agree on a plan with the team. Please walk me through your approach.

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How did you prove it was the cause? What would you look at, and who would you ask?
2. What would you monitor afterwards? Which alert would you set up, and on which number?
3. What is the trade-off of your fix? What could break for existing clients, and how would you roll it out?

**Key vocabulary**
- HTTP status code (2xx / 4xx / 5xx)
- response body / error payload
- API contract
- to surface an error to the user
- monitoring / error rate dashboard
- backward compatibility
- client-side vs. server-side handling
- "to agree on a convention with the team"

## Case P02: The order endpoint suddenly returns a 500

**Interview prompt.** Hi, this is an on-call story from our order service. After a recent change, one endpoint that returns an order started failing. The client gets a 500 error. In the logs you find an exception with the message "could not initialize proxy - no Session". The strange part: the same code worked fine on a developer's machine and in some other places, and the exception only shows up when the order is being converted to JSON for the response. The query itself looks fine and returns data, there are no database errors, and the database is healthy. The team lead pings you: "Can you take this? We need the endpoint back before the next release." Please walk me through how you would investigate and what you would say to the team.

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How did you prove it was the cause? How would you reproduce it locally?
2. What would you monitor or test afterwards so it does not come back?
3. What is the trade-off of your fix? What could get worse, for example performance or the shape of the API response?

**Key vocabulary**
- stack trace / exception message
- to serialize an object to JSON
- transaction boundary / session scope
- lazy loading vs. eager loading
- DTO (data transfer object)
- to reproduce locally
- regression
- "it works on my machine"

**Speaking challenge.** Set a timer for 90 seconds. Practice pronouncing the tricky words aloud: "serialize" (SEER-ee-uh-lize), "exception", "transaction", "proxy". Then explain the incident to your team lead and write your full answer below.
