## Case P19: One request's ID shows up in another request's logs

**Interview prompt.** Hi, this one comes from the on-call channel. Last night a teammate was tracing a customer complaint through our logs. Every request in our service gets a request ID, and we normally search by that ID to follow a request from start to finish. This time, he found log lines for request B that carried the request ID of request A. So the trace for A was polluted with lines that clearly belonged to B, and he could not trust the timeline. It does not happen all the time, and it is more visible when traffic is busy. There were no errors and no failed requests, so customers are fine, but our on-call people now doubt every log search they do. You are the engineer who picks this up. Please walk me through how you would handle it.

**Follow-up questions**
1. How did you prove it was the cause? How did you reproduce it?
2. What would you monitor or test afterwards so this does not come back?
3. What is the trade-off of your fix, and what would you tell the team who rely on these logs?

**Key vocabulary**
- request ID / correlation ID / trace ID
- to propagate context
- log correlation
- to reproduce under concurrent load
- observability (stress: ob-ZUR-vuh-bil-i-tee)
- intermittent / non-deterministic
- to rule out (a hypothesis)
- regression test

**Speaking challenge:** 90 seconds aloud first. Tip: "intermittent" is /ˌɪntərˈmɪtənt/ - stress the third syllable. Practice the sentence: "The failure was intermittent, so I first needed a reliable way to reproduce it."

## Case J19: The search page returns 400 when the filter is empty

**Interview prompt.** Hello, this is a ticket from the QA team. On our search page, users can type in a few filters, for example a keyword or a category, and press Search. If the user fills in the filters, everything works. But when the user leaves a filter empty and presses Search, the page shows an error, and in the browser network tab we can see the API answered with HTTP 400. The front-end developer says the page is just sending what the user typed, and the user is not supposed to see an error for leaving a box blank. Other endpoints in the same service work fine. It happens every time, so it is easy to reproduce. The ticket is marked low priority, but it affects the main search flow. You pick it up. Please walk me through how you would handle it.

**Follow-up questions**
1. How did you prove it was the cause? What exact request did you send?
2. What would you monitor or test afterwards so this does not come back?
3. What is the trade-off of your fix? Would you change the front end, the back end, or both, and why?

**Key vocabulary**
- HTTP 400 Bad Request (client error vs server error)
- request parameter / query string
- optional vs required parameter
- to reproduce with curl or Postman
- API contract
- input validation
- backward compatible
- edge case

**Speaking challenge:** 90 seconds aloud first. Tip: say "parameter" as /pəˈræmɪtər/ (stress the second syllable) and "curl" as /kɜːrl/. Practice the sentence: "First I reproduced it with curl, so I could separate the front end from the back end."
