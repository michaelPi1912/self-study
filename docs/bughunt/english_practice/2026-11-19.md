## Case J08: The import said "success", but 30 rows are missing

**Interview prompt.** Hi, this one came in from the support team this morning. We have a feature where operations staff upload an Excel file to import data into our system. Yesterday a user uploaded a file with a few hundred rows. The screen showed a green message: "Import successful". Later, the user noticed that 30 rows from the file were not in the database. They uploaded the file again and got the same green message and the same result. There are no error alerts, nobody got an error page, and the application logs look quiet. The user is frustrated because they trusted the message and already told their manager that all the data was loaded. The support lead asks you to find out what happened and make sure it cannot happen silently again. Please walk me through your approach.

**Follow-up questions**
1. How did you prove it was the cause? What evidence would you show the support lead?
2. What would you monitor or report to the user afterwards?
3. What is the trade-off of your fix? For example, should one bad row stop the whole file?

**Key vocabulary**
- a silent failure
- to swallow an exception
- partial success / all-or-nothing
- an error report for the user
- to log with enough context (row number, file name)
- to fail fast vs. to fail gracefully
- data integrity / reconciliation (comparing counts)
- a misleading success message

## Case M04: The customer paid, but the order can never be delivered

**Interview prompt.** Hi, this is a tough one from our e-commerce platform. We split our system into separate services: an order service, a payment service, and an inventory service. Last night during a busy period, a few customers placed orders. For these orders, the payment succeeded and the money left the customer's account. But the call to the inventory service failed, so the stock was never reserved. Now we have paid orders that we cannot ship, and the customers are waiting. Our team cannot just "roll back" like in a single database transaction, because the data lives in different services and different databases. Finance is asking about refunds and the CTO wants a design so this does not leave customers in a broken state again. You are the senior engineer on call. Please walk me through your approach.

**Follow-up questions**
1. How did you prove it was the cause? Could you reproduce it in a test environment?
2. What would you monitor afterwards? How would you know an order is stuck halfway?
3. What is the trade-off of your design? What do you give up compared with a single database transaction?

**Key vocabulary**
- a distributed transaction
- eventual consistency
- a compensating action
- orchestration vs. choreography
- idempotency / safe to retry
- a partial failure
- a stuck or "half-finished" order
- a dead-letter queue / manual reconciliation
