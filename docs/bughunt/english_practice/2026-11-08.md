## Case P43: Green on my laptop, red on CI

**Interview prompt.** Hi, this one is from our delivery team. We have a set of integration tests for the data layer. On every developer's laptop they run against an in-memory H2 database, and they all pass. A teammate opened a pull request yesterday, everything was green locally, and he was ready to merge. Then the pipeline ran the same integration tests against a real PostgreSQL instance, and some of them failed. Nobody changed the test code between the two runs, and the failure is repeatable, not flaky. The team lead is worried because the same code could behave differently in production, which also uses PostgreSQL. Developers are starting to say "just ignore CI, it works on my machine". You are the engineer asked to sort this out. Please walk me through how you would handle it.

**Follow-up questions**
1. How did you prove it was the cause? What exactly did you compare between the two environments?
2. What would you monitor or change in the pipeline afterwards so this does not come back?
3. What is the trade-off of your fix? For example, would your tests become slower or harder to run locally?

**Key vocabulary**
- "works on my machine"
- integration test vs unit test
- in-memory database
- environment parity (dev/prod parity)
- to diverge / behavioural difference
- repeatable vs flaky test
- CI pipeline / to gate a merge
- false sense of confidence

**Speaking challenge:** 90 seconds aloud first. Tip: say "PostgreSQL" as "post-gres-Q-L" (/ˈpoʊstɡrɛs kjuː ɛl/) and "integration" as /ˌɪntɪˈɡreɪʃn/. Practice the sentence: "The test was green locally, but green only proves something if the environment looks like production."

## Case P47: The container keeps getting killed, but the heap limit looks fine

**Interview prompt.** Hi, this is from the platform team. One of our Java services runs in Kubernetes. The JVM is started with a maximum heap of 512 megabytes, and the container's memory limit is 768 megabytes, so on paper there is plenty of room. But every few hours the pod is killed, and Kubernetes reports the reason as OOMKilled. Our heap graphs look healthy and never reach the 512 megabyte limit, and there is no OutOfMemoryError in the application logs at all. The pod restarts, works fine for a while, and then it happens again. Users see short bursts of errors each time it restarts. The team has already argued about whether to just raise the limit, but nobody can explain the numbers. You own this service. Please walk me through how you would handle it.

**Follow-up questions**
1. How did you prove it was the cause? What metrics or commands would you look at?
2. What would you monitor or alert on afterwards?
3. What is the trade-off of your fix? Would it cost more money, or change performance?

**Key vocabulary**
- OOMKilled / exit code 137
- memory limit vs memory request
- container resource limits
- JVM flags (e.g. -Xmx)
- to profile memory usage
- observability / dashboards
- capacity planning / headroom
- rolling restart / blast radius

**Speaking challenge:** 90 seconds aloud first. Tip: say "Kubernetes" as /ˌkuːbərˈnɛtiːz/ and "OOMKilled" as "O-O-M-killed". Practice the sentence: "The heap graph was healthy, so I stopped trusting it as the only source of truth."
