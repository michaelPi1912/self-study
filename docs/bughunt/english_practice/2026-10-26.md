## Case M24: Every small change breaks something else

**Interview prompt.** Hi, welcome to the team. Let me describe a problem we live with every sprint. We have a class called `OrderService`. It started small, but over the years it has grown to around three thousand lines. Last week a developer changed one small rule about how a discount is shown, a change that should have taken ten minutes. After the release, a refund flow and an email notification stopped working. The sprint before, a tiny fix in a status update broke the reporting page. Now nobody wants to touch this class, and every pull request on it takes days because reviewers are afraid. Our manager asks you, as the new middle-level engineer, to explain what is going on and how you would deal with it without stopping feature work. How would you approach it?

**Follow-up questions**
1. How would you prove, with evidence, where the real problems are, and not just rely on your feeling about the code?
2. What would you do first when the test coverage of this class is low?
3. What is the trade-off of your approach? How do you convince the business to invest time in it?

**Key vocabulary**
- tightly coupled / high cohesion
- code smell
- regression
- blast radius
- to refactor incrementally
- safety net (tests) / characterization test
- technical debt
- separation of concerns

## Case P07: The exception was thrown, but the data was saved anyway

**Interview prompt.** Hi, let's do a quick incident scenario. This morning, support reported a strange case. A customer's file export failed and the user saw an error on the screen. But when the support engineer checked the database, the order record from the same request was already saved, as if nothing had gone wrong. The method that handles this request is annotated with `@Transactional`, and the code clearly throws an `IOException` when the file step fails. The team lead says: "We threw an exception, so I expected nothing to be saved." Finance is now asking why they see orders without the matching files. You are on call. Please walk me through how you would investigate and explain it to your team.

**Follow-up questions**
1. How did you prove it was the cause? What would you check in the logs or in a test?
2. What would you monitor or test afterwards so you notice a similar problem earlier?
3. What is the trade-off of your fix? Could it change behavior for other methods in the project?

**Key vocabulary**
- transaction boundary
- to commit / to roll back
- unexpected data state (inconsistent data)
- to reproduce with an integration test
- to enable debug logging for transactions
- data inconsistency / data cleanup
- atomicity
- default behavior vs. explicit configuration
