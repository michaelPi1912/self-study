## Case M15: A few dozen 502s on every deploy

**Interview prompt.** Hi, this one is from our release channel, and it is getting on people's nerves. We deploy our Spring Boot service with a rolling deployment, one instance at a time, behind a load balancer. The deploy itself looks healthy: new instances start, the pipeline turns green, nobody touches anything manually. But every single time we roll out, the monitoring shows a few dozen 502 errors from the gateway. It is not a huge number compared to our traffic, but it happens on every release, and it is always during the rollout window. Customers occasionally see failed requests, and support has started to notice the pattern. The product owner is asking why a "zero-downtime" deploy is not zero-downtime. The engineering manager wants you to explain what you would investigate, and how you would make releases clean. Please walk me through your approach.

**Follow-up questions**
1. How did you prove it was the cause? What logs, metrics, or experiments did you use?
2. What would you monitor afterwards to be sure releases stay clean?
3. What is the trade-off of your fix? Does it cost anything in deploy time or complexity?

**Key vocabulary**
- rolling deployment / zero-downtime deploy
- in-flight requests
- graceful shutdown
- load balancer / health check
- 502 Bad Gateway
- to drain connections
- readiness vs. liveness probe
- rollout window

## Case J11: The error page says too much

**Interview prompt.** Hi, this one came from a security review, and the reviewer was not happy. During a routine penetration test, a tester sent a malformed request to one of our REST endpoints on purpose. Instead of a short, friendly error, the response body came back with a lot of internal detail. It contained the names of our Java classes, a full SQL statement, and even file paths from the server. Nothing was actually hacked, but the tester wrote it up as a finding, because an attacker could learn how our system is built just by sending bad input. The application works normally for valid requests, so nobody noticed before. The security lead asks you to explain why this is a problem, how you would investigate it, and how you would make sure it never happens again. Please walk me through your approach.

**Follow-up questions**
1. How did you prove it was the cause? How would you reproduce it safely?
2. What would you monitor or test afterwards so it cannot come back?
3. What is the trade-off of your fix? Could it make debugging harder for the team?

**Key vocabulary**
- information disclosure / information leakage
- stack trace
- attack surface
- penetration test (pen test) / security finding
- to sanitize error responses
- correlation ID
- to log server-side vs. to expose to the client
- least privilege

**Speaking challenge:** say your six steps aloud in 90 seconds. Practise "sanitize" (/ˈsænətaɪz/), "vulnerability" (/ˌvʌlnərəˈbɪləti/) and "disclosure" (/dɪsˈkloʊʒər/).
