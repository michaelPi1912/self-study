## Case M01: Money transfers randomly fail with a deadlock error

**Interview prompt.** Hi, let's try an on-call scenario. We run a small wallet feature where users can transfer money between their own accounts. Since last week, support has been receiving complaints: now and then a transfer fails and the user has to retry. It does not happen all the time, mostly during busy hours, and never when you test alone on your laptop. When you open the application logs, you see the same message again and again: "Deadlock found when trying to get lock; try restarting transaction". The failing requests often involve two accounts that send money to each other at almost the same moment. The business team is nervous, because failed transfers look very bad to customers. You are the engineer on call. Please walk me through how you would investigate this and what you would tell the team.

**Follow-up questions**
1. How did you prove it was the cause? What would you look at in the database or in the logs?
2. What would you monitor afterwards to be sure the problem is really gone?
3. What is the trade-off of your fix? Could it hurt throughput or change behavior for other flows?

**Key vocabulary**
- deadlock / lock contention
- concurrent transactions
- to acquire a lock / lock ordering
- to reproduce under load
- retry with backoff
- isolation level
- the database engine status output (e.g. "latest detected deadlock")
- data consistency / idempotency

## Case P10: A paginated list works, but the server eats memory

**Interview prompt.** Hi, here is a scenario from a recent release. We added a screen that shows a list of orders with their items, with pages of 20 records. In development everything looked fine and the response was correct. After the release, the operations team noticed that the memory of the service grows a lot when this endpoint is called, and the response time gets worse as the table grows. When you check the startup and request logs, you find a warning with the code HHH90003004, which says that the pagination is being applied in memory. The data volume in production is much bigger than in dev, so the team is worried that the service may run out of memory during a busy day. You are asked to explain what is happening and what you would do. How would you approach it?

**Follow-up questions**
1. How did you prove it was the cause? What would you check in the logs, the SQL, or a test?
2. What would you monitor afterwards, so you notice a similar problem earlier?
3. What is the trade-off of your fix? Does it change the shape of the data or the number of queries?

**Key vocabulary**
- pagination / page size
- in-memory vs. database-level
- to load the whole result set
- heap usage / memory pressure
- to inspect the generated SQL
- number of queries / round trips
- to reproduce with realistic data volume
- log warning vs. silent performance problem
