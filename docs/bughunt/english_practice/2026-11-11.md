## Case M23: The PM wants an incident report in English

**Interview prompt.** Hi, this one is a bit different from a pure bug. Last week our team had a production incident, and it is now resolved. Today the product manager wrote to you in the team channel: she needs an incident report in English by tomorrow, because it will go to a foreign client and to our leadership. She asked for four things: what happened, what the impact was, what the cause was, and what we will do to prevent it. Some people on the team are nervous, because they think the report will be used to find someone to blame. Others just want to write "a bug in code, fixed, sorry" and move on. You are the engineer who was on call, so the PM expects you to write it. Please walk me through how you would approach this report, and what you would send to the PM.

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How do you make the report factual and useful without blaming a person? Can you give me an example sentence?
2. How do you make your prevention actions concrete? How will we know in three months that they worked?
3. What is the trade-off between a short report for a manager and a detailed one for engineers? How would you handle both readers?

**Key vocabulary**
- incident report / postmortem / RCA (root cause analysis)
- blameless culture
- timeline of events
- customer impact / blast radius
- contributing factors
- action items (with owner and due date)
- to mitigate / mitigation
- lessons learned

**Pronunciation tips:** "mitigate" = /ˈmɪtɪɡeɪt/; "postmortem" = /poʊstˈmɔːrtəm/; "analysis" = /əˈnæləsɪs/ (stress on "nal").

## Case P14: Searching by the end of an order code is very slow

**Interview prompt.** Hi, this one came from the support team. They have a search box where they type the last few characters of an order code, for example the last five or six, because customers often read only the end of the code over the phone. The search works and returns the right orders, but it has become very slow, and on a big table it is almost unusable. The team says the column is indexed, and other lookups on the same table are fast. Only this kind of search, "ends with these characters", is slow. The table keeps growing, so it gets worse every month. You are the engineer who picks this up. Please walk me through how you would handle it.

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How did you prove it was the cause? Which tool or command did you use, and what did you look for in the output?
2. What would you monitor afterwards, and how would you test your fix on production-size data?
3. What is the trade-off of your fix? Does it cost anything for writes, storage or maintenance?

**Key vocabulary**
- query plan / execution plan
- full table scan
- wildcard / pattern matching
- to run `EXPLAIN ANALYZE`
- index selectivity
- full-text search
- trade-off (read speed vs. write cost)
- to benchmark / baseline

**Pronunciation tips:** "wildcard" = /ˈwaɪldkɑːrd/; "index" (plural "indexes" or "indices") = /ˈɪndeks/; "benchmark" = /ˈbentʃmɑːrk/.
