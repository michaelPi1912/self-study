## Case P01: The orders list page is slow

**Interview prompt.** Hi, this one came from the support team this morning. We have an admin page that shows a list of 50 orders. Customers-care staff open it all day, and it has become painfully slow: about 2 seconds per page load. Nobody changed the front end. A teammate turned on SQL logging in a test environment and noticed something odd: a single request to this page printed 51 SQL statements in the log. The data on the page is correct, and there are no errors or exceptions. The product owner asks you two things: why is this page slow, and can it be fixed before Monday's promotion, when traffic will be much higher? Please walk me through your approach.

**Follow-up questions**
1. How did you prove it was the cause? What exactly did you measure before and after?
2. What would you monitor afterwards so the problem does not come back quietly?
3. What is the trade-off of your fix? Could it make some other page slower or use more memory?

**Key vocabulary**
- latency / response time
- to enable SQL logging
- query count per request
- to profile an endpoint
- baseline vs. after-fix measurement
- to reproduce locally with test data
- performance regression
- to scale under load

**Speaking challenge:** say your six steps aloud in 90 seconds. Practise "latency" (/ˈleɪtnsi/), "SQL" (either "S-Q-L" or "sequel", but stay consistent) and "query" (/ˈkwɪəri/).

## Case P47: The pod keeps getting killed

**Interview prompt.** Hi, this one is from the platform team. Our Spring Boot service runs in Kubernetes. The container has a memory limit of 768Mi, and we start the JVM with `-Xmx=512m`, so on paper there is a comfortable 256 megabytes of room. Even so, the pod is being killed again and again, and `kubectl describe pod` shows the reason `OOMKilled`. It restarts and works for a while, then dies again, sometimes after a few hours and sometimes faster under load. There is no `OutOfMemoryError` in the application logs, which confuses the team. Users see a few failed requests at each restart. The on-call engineer asks you to explain why the pod dies and to propose a safe change. Please walk me through your approach.

**Follow-up questions**
1. How did you prove it was the cause? Which tools or metrics did you use?
2. What would you monitor and alert on afterwards?
3. What is the trade-off of your fix? Does it change cost, performance or the number of pods we need?

**Key vocabulary**
- memory limit / resource request
- OOMKilled / exit code 137
- heap size (-Xmx)
- container memory usage vs. JVM memory
- to restart / crash loop
- to take a heap dump / to inspect metrics
- headroom
- graceful degradation

**Speaking challenge:** read your answer aloud for 90 seconds. Practise "Kubernetes" (/ˌkuːbərˈnetiːz/), "heap" (/hiːp/), and say "OOMKilled" as "O-O-M killed".
