## Case P04: The "preview price" feature changes the database

**Interview prompt.** Hi, this one came in from the support team this morning. We have a "preview price" feature: a sales person picks a product, types a discount, and the page shows what the new price would look like. It is meant to be read-only, just a calculation on screen. Today, a customer complained that a product's price in the catalogue was different from yesterday. We checked the audit trail and nobody edited that product. Then we noticed the timestamp matches a moment when a sales person was only "previewing" a price. The service method does not call `save()` anywhere, and the team is confused about how the database value changed. Support wants to know what happened, how many products may be affected, and how to stop it. How would you handle this?

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team.

**Follow-up questions**
1. How did you prove it was the cause? Can you reproduce it with a test?
2. What would you monitor afterwards, and how would you find other places with the same problem?
3. What is the trade-off of your fix? Does it change performance or code readability?

**Key vocabulary**
- unexpected write / unintended update
- read-only operation
- transaction boundary
- to reproduce the issue
- audit trail / audit log
- regression test
- blast radius ("how many records are affected")
- to roll back / to restore the data

**Speaking challenge:** say your six steps aloud in 90 seconds. Practise "transaction" (/trænˈzækʃn/), "unintended" (/ˌʌnɪnˈtendɪd/) and "audit" (/ˈɔːdɪt/).

## Case J02: The shopping cart shows the same product twice

**Interview prompt.** Hello, this is from the front-end team. In the shopping cart page, a customer sees two separate lines for the same product, for example two lines of the same T-shirt, same size, same colour. The backend code stores the cart items in a `HashSet<CartItem>`, so we all assumed duplicates were impossible. The `CartItem` class already has an `equals()` method that compares product and size, and the unit test for `equals()` passes. Still, when two identical items are added, the page shows two lines and the cart total is too high. Customers are annoyed because they think they are being charged twice. Can you tell me how you would investigate this and what you would do before the next release?

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team.

**Follow-up questions**
1. How did you prove it was the cause? What small test would you write?
2. What would you monitor afterwards, or what code review check would catch this kind of problem?
3. What is the trade-off of your fix? Is there anything risky about using mutable objects in a set?

**Key vocabulary**
- duplicate entries
- HashSet / collection
- to compare objects for equality
- unit test passes but behaviour is wrong
- to reproduce with a minimal example
- cart total / double charge
- code review checklist
- to behave unexpectedly

**Speaking challenge:** say your six steps aloud in 90 seconds. Practise "duplicate" (noun /ˈduːplɪkət/, verb /ˈduːplɪkeɪt/), "equality" (/iˈkwɒləti/) and "collection" (/kəˈlekʃn/).
