## Case M11: Timeouts that arrive in waves

**Interview prompt.** Hi, this one is from the on-call channel last night. We run a Spring Boot service that other internal services call over HTTP. Nothing is crashing, and the health checks stay green. But every few minutes, the callers report a burst of timeouts. Then, a little later, everything is normal again, and the next wave comes after a similar gap. The callers' own dashboards show retries piling up during each burst, and some of them started failing their own requests as a result. Our service shows no errors in its logs during these windows, which makes it even more confusing. The team lead asks you to explain what you would look at first, how you would narrow it down, and how you would stop it from happening again. Please walk me through your approach.

**Follow-up questions**
1. How did you prove it was the cause? What data or experiment would convince a sceptical colleague?
2. What would you monitor afterwards, and what alert would you set?
3. What is the trade-off of your fix? Does it cost anything in memory, throughput, or complexity?

**Key vocabulary**
- intermittent / periodic issue
- cascading failure (timeouts spreading to callers)
- request timeout vs. connect timeout
- latency percentiles (p95, p99)
- retry storm
- correlating metrics with the timeline
- observability / metrics dashboard
- to rule out a hypothesis

**Speaking challenge:** say your six steps aloud in 90 seconds. Practise "latency" (/ˈleɪtənsi/), "intermittent" (/ˌɪntərˈmɪtənt/) and "cascading" (/kæsˈkeɪdɪŋ/).

## Case P45: Full coverage, still a production bug

**Interview prompt.** Hi, this one came out of a retro meeting, and the discussion was a bit heated. Our team is proud of the test suite: the CI report shows 100% code coverage on the module that calculates order amounts, and a coverage gate blocks any pull request that lowers it. Last week, production still threw errors for a few customers. After digging into the logs, we found the failing inputs were unusual values: zero, a negative number, and a null in a field that "should never be empty". The code had been executed by tests many times, so the report said everything was covered. A manager asked, "How can we have 100% coverage and still ship a bug?" The team now wants a clear answer, and a practical plan. Please walk me through how you would explain it, how you would investigate, and what you would change in the way we test.

**Follow-up questions**
1. How did you prove which inputs were missing? How would you reproduce the production failure in a test?
2. What would you monitor or measure afterwards, besides line coverage?
3. What is the trade-off of your approach? Could it slow down the team or make the test suite harder to maintain?

**Key vocabulary**
- code coverage vs. test quality
- boundary values / edge cases
- parameterized test
- to assert on behavior, not on implementation
- null safety / input validation
- false sense of security
- regression test
- mutation testing (as an idea to mention)

**Speaking challenge:** say your six steps aloud in 90 seconds. Practise "coverage" (/ˈkʌvərɪdʒ/), "boundary" (/ˈbaʊndri/) and "parameterized" (/pəˈræmətəraɪzd/).
