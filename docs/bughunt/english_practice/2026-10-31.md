## Case P13: We added an index, but the report is still slow

**Interview prompt.** Hi, here is a scenario from last sprint. Our orders table has grown to tens of millions of rows. A teammate noticed that the "recent orders" report was slow, so they added an index on (status, created_at) and shipped it with confidence. A week later, the product owner comes back and says the report is still slow. You check, and the index really exists in production. The report query filters on created_at to get the orders from the last few days. In staging, with a small dataset, everything looks fine, so nobody can see the problem there. The teammate is a bit upset: "I added the index, why is nothing better?" You are asked to join the call. Please walk me through how you would investigate and what you would say to the team.

**Follow-up questions**
1. How did you prove it was the cause? What exactly would you run, and what would you look for in the output?
2. What would you monitor afterwards to be sure the query stays fast as the table keeps growing?
3. What is the trade-off of your fix? Could it affect write performance, disk usage, or other queries?

**Key vocabulary**
- execution plan / `EXPLAIN` (and `EXPLAIN ANALYZE`)
- full table scan
- composite index
- query selectivity
- slow query log
- to verify against production-like data
- write overhead of an index
- "the index exists, but the optimizer does not use it"

## Case M16: Rename a column on a 50-million-row table with zero downtime

**Interview prompt.** Let's try a planning scenario. Our biggest table has about 50 million rows and sits behind the checkout flow, which is busy at all hours. Product and engineering agreed on a cleanup: one column has a confusing name, and the team wants it renamed. The business requirement is clear and strict: no downtime, not even a short maintenance window. Several services read this table, and some of them are deployed on different schedules, so you cannot upgrade everything at the same moment. A teammate suggests, "It is only one line of SQL, let's run it on Saturday night." You are the engineer who has to own this change. Please walk me through how you would approach it and what you would tell the team before anything is executed.

**Follow-up questions**
1. How would you prove the plan is safe before touching production? What would you test?
2. What would you monitor while the change is running and afterwards?
3. What is the trade-off of your approach? How long does it take, and what is the cost in complexity?

**Key vocabulary**
- zero-downtime migration
- backward compatible / backward compatibility
- rolling deployment
- to roll back / rollback plan
- table lock / metadata lock
- backfill (in batches)
- feature flag / phased rollout
- to deprecate and then remove
