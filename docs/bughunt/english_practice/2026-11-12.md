## Case P43: Green on my laptop, red on CI

**Interview prompt.** Hi, this one came up in our team channel this morning. A colleague, Linh, finished a feature and ran the integration tests on her laptop. Everything was green, so she opened a pull request. A few minutes later the CI pipeline went red. The failing tests are integration tests that talk to the database. Locally, the tests run against an in-memory H2 database. On CI, the same tests failed, and the failure comes from the real PostgreSQL that production uses. Nobody changed the test code between the two runs. The team is now a bit nervous, because one more thing like this and people will stop trusting the test suite. Linh asked you to pair with her for 30 minutes. Please walk me through how you would handle it.

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How did you prove it was the cause? Which log, error message or command told you where the two environments differ?
2. What would you monitor or check afterwards, so this kind of failure is caught earlier next time?
3. What is the trade-off of your fix? Think about test speed, developer experience and CI cost.

**Key vocabulary**
- "It works on my machine" / "environment parity"
- integration test vs. unit test
- in-memory database
- flaky test / reproducible failure
- to reproduce the failure locally
- CI pipeline (to go red / to go green)
- to run against a real database
- "the tests gave us a false sense of security"

## Case J21: The test that fails at midnight

**Interview prompt.** Hi, here is a story from our last sprint. We have a test called "order expires today". It checks that an order whose expiry date is today is handled as expired. During the working day this test is always green, for everyone, on every laptop. But our CI also runs a nightly build, and when the build starts around midnight, the same test goes red. Sometimes it is green again if you re-run it the next morning, so people started calling it "the ghost test" and some wanted to disable it. The code under test did not change, and the test code did not change either. The team lead asked you to take a look before anyone deletes it. Please walk me through how you would approach it.

**Answer frame:** Situation -> What I investigated -> Root cause -> Fix -> How I would prevent it -> What I would tell the team

**Follow-up questions**
1. How did you prove it was the cause? Can you reproduce the failure on demand, without waiting for midnight?
2. What would you monitor afterwards, and how would you keep a similar test from coming back?
3. What is the trade-off of your fix? Does it change how the production code is written?

**Key vocabulary**
- flaky test / non-deterministic test
- "it fails intermittently"
- time-dependent behaviour
- to reproduce on demand
- edge case / boundary condition
- to quarantine vs. to fix a test
- nightly build
- deterministic (and "to make the test deterministic")
